# RoleFit Canvas

> 지원할 회사의 공고와 나의 이력을 연결해, **무엇을 보여주고 무엇을 더 준비할지** 알려주는 웹앱.

「RoleFit Canvas 앱 기획서 v4.0」(MindCanvas, 2026.09.11)의 구현체입니다.
하나의 지원 건에서 서로 다른 독자를 가진 **두 결과물**을 함께 만듭니다.

| | 결과물 01 · 기업 제출용 | 결과물 02 · 지원자 전용 |
|---|---|---|
| 무엇 | 맞춤형 Resume / CV | 지원전략 분석서 |
| 답하는 질문 | "나를 어떻게 보여줄 것인가" | "어디가 맞고 무엇을 더 준비할 것인가" |
| 공개 범위 | 사용자 확인 후 제출 | 기본 비공개 |

## 분석 파이프라인

```
JD 분석                내 이력 분석
(인재상 + requirements)  (경력·학위·프로젝트·활동)
      │                      │
      └──────────┬───────────┘
                 ▼
   ① 직접 매핑 (baseline)      →  현재 매칭률      →  이력서 1 · Baseline
                 ▼
   ② 스토리텔링 매핑 (최대치)    →  스토리텔링 후     →  이력서 2 · 제출용  ★
                 ▼
   ③ 개선 과제 + 목표          →  목표 매칭률      →  이력서 3 · 미래(계획)
```

매칭 3단계와 이력서 3판본이 **1:1로 대응**합니다. 같은 근거로 점수가 매겨지고 같은 근거로 문장이 쓰입니다.

### 세 판본의 차이

| 판본 | 담는 내용 | 제출 |
|---|---|---|
| **1 · Baseline** | 직접 수행한 사실만. 모든 문장이 직접 근거를 가짐 | 가능 |
| **2 · 제출용** ★ | 이미 가진 관련 경험까지 이 직무와 연결해 설명 | **기본 제출본** |
| **3 · 미래(계획)** | 실행 과제를 완료했을 때의 모습. `[예정]` 표시 | **불가** |

> 이력서 3은 지원자 전용 계획 미리보기입니다. 아직 사실이 아닌 항목이 들어 있어 제출용으로 내려받을 수
> 없습니다. 기획서 06의 "예정된 학위·자격·교육·프로젝트는 완료된 이력서 항목으로 넣지 않는다"를 코드로
> 강제한 것입니다.

## 설계에 못박은 원칙

기획서의 서술 원칙을 주석이 아니라 **타입과 테스트로** 강제했습니다.

| 원칙 | 어디서 강제되는가 |
|---|---|
| 수치는 합격확률이 아니라 **직무 매칭률** | 화면 용어 통일, `READING_NOTE`를 결과 화면마다 고정 |
| 근거 없는 내용은 만들지 않는다 | 모든 점수·문장이 `EvidenceRef`를 참조. 없으면 `needs-confirmation` |
| 사실과 앱의 해석을 구분한다 | `RationaleNote`가 `evidence`(원문 인용)와 `interpretation`(해석)을 분리 |
| **문장만 고쳐도 점수가 오르지 않는다** | `afterStory`는 실제 관련 경험이 있을 때만 상승 |
| **체크만으로 목표 점수를 주지 않는다** | `reassess()`가 `evidence-submitted` + 증거 설명이 있는 과제만 반영 |
| 총점과 필수 조건은 다른 정보 | `MustHaveStatus`를 총점과 별도로 계산·표시 |
| 학력·수료를 실무 연수로 바꾸지 않는다 | 경력연수 부문은 `target`에 미래 개월을 더하지 않음 (`targetCaveat`) |
| 분석서를 이력서에 자동 포함하지 않는다 | 두 문서가 별도 빌더·별도 파일로 분리 |

기획서 03의 검증 수치(**32.75 → 45.25 → 71.50**, 화면 **33 → 45 → 72**)는 회귀 테스트로 고정되어
있습니다 — `src/lib/__tests__/scoring.test.ts`.

## 로그인과 회원 관리

로그인은 **선택**입니다. 로그인하지 않아도 샘플 체험과 내 자료 분석을 전부 쓸 수 있습니다.
로그인은 여러 기기에서 같은 계정으로 이어 쓰고, 운영자가 이용 현황을 보기 위한 것입니다.

- **Google 계정으로 로그인·가입** — 첫 로그인이 곧 가입입니다.
  공개 클라이언트 ID 하나만 쓰고 비밀키는 쓰지 않으므로 정적 배포에서도 동작합니다.
- **소유자** — `linkedsugi@gmail.com` 은 코드에 소유자로 고정되어 있습니다.
  권한을 내리거나 정지·삭제할 수 없습니다. 관리자 전원이 서로 권한을 내려
  아무도 들어갈 수 없게 되는 상황을 막기 위한 것입니다.
- **회원 관리** (`/admin`) — 관리자만 볼 수 있습니다.
  권한 변경, 이용 정지·해제, 운영 메모, 삭제, 검색.

> **관리자도 회원의 지원 자료를 볼 수 없습니다.** 회원 관리 화면에 보이는 것은 계정 정보
> (이름·이메일·로그인 기록)뿐입니다. 공고·이력·분석서는 그 사람의 기기에만 있습니다.

### 권한이 실제로 강제되는 곳

브라우저 안에서 하는 검사는 브라우저를 쓰는 사람에게 언제든 우회됩니다.
그래서 회원 목록을 읽고 권한을 바꾸는 일은 **서버가 Google ID 토큰의 서명을 검증**한 뒤에만
허용합니다 (`src/lib/auth/verify.ts`, `/api/members`).

| 배포 | 회원 목록 | 권한 강제 |
|---|---|---|
| 서버 있음 (`ROLEFIT_DATA_DIR` 설정) | 서버에 보관, 전체 가입자 | 서버가 토큰 서명 검증 |
| 서버 있음 (설정 없음) | 서버 메모리, 재시작 시 소멸 | 서버가 토큰 서명 검증 |
| 정적 (GitHub Pages) | **브라우저마다 따로** | 화면 수준 (경계 아님) |

정적 배포에서는 이 한계를 관리 화면 상단에 그대로 표시합니다. 숨기지 않습니다.

## 시작하기

```bash
npm install
npm run dev        # http://localhost:3000
```

키 없이 바로 동작합니다. 규칙 기반 분석 엔진이 기본입니다.
정밀 분석을 켜려면 `.env.local`에 `ANTHROPIC_API_KEY`를 넣으세요 (`.env.example` 참고).
키가 없으면 앱은 조용히 규칙 기반으로 계속 동작합니다.

```bash
npm run build      # 프로덕션 빌드
npm test           # 테스트
npm run lint
```

## 배포

GitHub Actions 가 타입 검사와 테스트를 통과한 뒤에만 GitHub Pages 로 올립니다.
깨진 배포본이 올라가지 않게 하기 위한 것입니다.

**최초 1회만 사람이 해야 하는 설정이 있습니다.**
저장소 **Settings → Pages → Build and deployment → Source** 를 **GitHub Actions** 로 바꾸세요.
워크플로 토큰에는 Pages 를 켤 권한이 없어 자동화할 수 없습니다.
켜기 전까지는 `build` 는 성공하고 `deploy` 만 실패합니다.

켜고 나면 배포 주소는 `https://<사용자>.github.io/<저장소>/` 입니다.

Google 로그인을 함께 쓰려면 두 가지가 더 필요합니다.

1. Google Cloud Console 에서 **웹 애플리케이션** 용 OAuth 클라이언트 ID 를 만들고,
   승인된 JavaScript 원본에 배포 주소(`https://<사용자>.github.io`)를 넣습니다.
2. 저장소 **Settings → Secrets and variables → Actions → Variables** 에
   `NEXT_PUBLIC_GOOGLE_CLIENT_ID` 를 추가합니다. 워크플로는 이미 이 값을 읽습니다.
   (공개 클라이언트 ID 라 Secrets 가 아니라 Variables 입니다 — 비밀이 아니고
   빌드 결과에 그대로 들어갑니다.)

설정하지 않아도 앱은 그대로 동작하고, 로그인 자리에는 "설정되어 있지 않습니다" 안내가 나옵니다.

### 서버가 있는 곳에 올릴 때

`npm run build && npm start` 로 Node 에서 돌리면 두 가지가 더 살아납니다.

- 공고 URL 을 서버가 대신 열어 옵니다 (정적 배포에서는 붙여넣기로 안내).
- 회원 정보를 서버에 보관하고, 서버가 토큰 서명을 검증해 관리자 권한을 강제합니다
  (`ROLEFIT_DATA_DIR` 설정 시 재시작해도 유지).

## 구조

```
src/
├─ lib/
│  ├─ types.ts          도메인 모델 — 유일한 진실
│  ├─ scoring.ts        가중 매칭률, 재평가, 지원 판단
│  ├─ templates.ts      기본 템플릿 5종
│  ├─ engine/           JD 분석 · 이력 분석 · 매핑 · 3판본 이력서 생성
│  ├─ export/           Word · 텍스트 · 인쇄(PDF) 내보내기
│  ├─ auth/             Google 로그인 · 회원 저장소 · 서버 토큰 검증
│  └─ samples/          데모 샘플 A~E
├─ store/               지원 건 상태 · 로그인 상태 (localStorage 보관)
├─ components/          화면과 UI 프리미티브
└─ app/                 라우트 · API
```

## 이 앱이 하지 않는 것

- 합격 확률을 예측하지 않습니다.
- 없는 경험을 만들어 넣지 않습니다.
- 대량 자동 지원이나 채용팀의 자동 후보 선별을 하지 않습니다.
- 직무와 무관한 나이·성별·외모·종교·가족관계로 인재상이나 점수를 만들지 않습니다.
- 낮은 점수로 불안을 자극하거나, 결제로 점수를 올리지 않습니다.

샘플의 회사·인물·수치는 모두 가상입니다.
